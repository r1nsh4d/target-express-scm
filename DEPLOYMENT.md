# Deploying to the Hetzner host

This machine already runs **Laam**. Everything below is built so the two never
touch each other. Read the isolation section before the first deploy.

## How the two applications stay apart

| Risk | How it is handled |
|---|---|
| Container name collision | Compose project pinned to `target-express`; containers prefixed `tx-` |
| Volume collision | Named volumes are namespaced by the project name |
| Network collision | Dedicated network `target-express-net` |
| Port collision | **One** published port, bound to `127.0.0.1`, set by `TX_HTTP_PORT` |
| Database collision | Postgres runs in its own container on the internal network, not on the host |
| Proxy collision | Separate vhost matched on `server_name`; Laam's config is not edited |
| Accidental teardown | Always pass `-f docker-compose.prod.yml`; never run a bare `docker compose down` from the wrong directory |

Postgres and MinIO publish **no ports at all** in production. They are reachable
only from the `api` container. That is deliberate: on a shared box, an exposed
database is the thing most likely to go wrong.

## 1. Preflight — run this first

```bash
git clone <repo> /opt/target-express
cd /opt/target-express
bash deploy/preflight.sh
```

It is read-only. It reports the host's running containers, existing compose
projects, every listening port, and which reverse proxy is active. **Send me
that output** and I will pin the ports and write the proxy config to match what
is actually free — rather than guessing around Laam.

If `18080` comes back busy, change `TX_HTTP_PORT` in `.env.prod`. Nothing else
needs to move.

## 2. Deploy — one script

```bash
bash deploy.sh --check    # report only, changes nothing
bash deploy.sh            # deploy or update
bash deploy.sh --seed     # also load demo data (Godrej masters, sample trips)
```

`deploy.sh` does the whole sequence and is safe to re-run:

1. Checks docker and the compose plugin are present and reachable
2. Creates `.env.prod` on first run, **generating the three secrets** — a deploy
   that silently comes up on a default key is worse than one that fails
3. Refuses to start if `TX_HTTP_PORT` is taken by something that is not ours,
   naming what holds it
4. Builds and starts, scoped to the `target-express` compose project
5. Waits for the API to report healthy, printing logs if it does not
6. Generates the initial migration on first deploy, then runs `upgrade head`
7. Prints the URL, the proxy next step, and the log/stop commands

Every command is scoped to the project, so nothing it does can touch Laam.

After the first run, edit `.env.prod` and set `PUBLIC_BASE_URL` and
`CORS_ORIGINS` to the real hostname — customer tracking links are built from
`PUBLIC_BASE_URL`, so a wrong value means dead links in customers' hands.

Then commit `backend/alembic/versions/` so the schema is version controlled.

## 2b. Configure by hand instead

```bash
cp .env.prod.example .env.prod
chmod 600 .env.prod
```

Fill in the three secrets:

```bash
openssl rand -hex 32      # SECRET_KEY
openssl rand -base64 24   # POSTGRES_PASSWORD
openssl rand -base64 24   # S3_SECRET_KEY
```

Set `PUBLIC_BASE_URL` and `CORS_ORIGINS` to the real hostname. Customer tracking
links are built from `PUBLIC_BASE_URL`, so if it is wrong the links a consignee
receives will point nowhere.

## 3. Bring the stack up

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
```

## 4. Migrate and seed

```bash
# First deploy only: generate the initial migration from the models.
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec api alembic revision --autogenerate -m "initial schema"

docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec api alembic upgrade head

# Demo data: Godrej masters, rate cards, worked trips. Skip on a real go-live.
docker compose -f docker-compose.prod.yml --env-file .env.prod \
  exec api python -m app.seed
```

> The autogenerated migration is written **inside the container**. Copy it back
> into the repo and commit it, or the next deploy regenerates from scratch:
> ```bash
> docker cp tx-api:/srv/alembic/versions ./backend/alembic/
> ```

## Day-to-day: one script per piece

`deploy.sh` does the whole thing. These three do one piece each, which is what
you want once it is running — rebuilding the frontend should not restart the
database.

```bash
bash deploy/db.sh --help          # Postgres, migrations, backups
bash deploy/backend.sh --help     # the FastAPI service
bash deploy/frontend.sh --help    # the built React app
```

Common ones:

| | |
|---|---|
| Frontend changed | `bash deploy/frontend.sh rebuild` |
| Backend changed | `bash deploy/backend.sh up` |
| Models changed | `bash deploy/db.sh makemigration "what changed"` |
| **This update adds a table** | `bash deploy/db.sh makemigration "enquiries"` — run it **before** `backend.sh up`, or the Enquiries screen 500s |
| Something is wrong | `bash deploy/backend.sh errors` |
| Before anything risky | `bash deploy/db.sh backup` |
| Check storage works | `bash deploy/backend.sh storage` |
| Is the real logo live? | `bash deploy/frontend.sh brand` |

Every command is scoped to the `target-express` compose project, so none of them
can reach another stack on the host. The two that destroy data — `db.sh restore`
and `db.sh reset` — make you type `yes` in full, and `reset` takes a backup
before it does anything.

**A frontend source change needs `rebuild`, not `restart`.** The app is compiled
into the image, so a restart just serves the previous build.

## 5. Reverse proxy

Pick the one the host already runs — the preflight output says which.

**nginx**
```bash
sudo cp deploy/nginx-site.conf.example /etc/nginx/sites-available/target-express
sudo nano /etc/nginx/sites-available/target-express      # set server_name + port
sudo ln -s /etc/nginx/sites-available/target-express /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d targetexpress.example.com
```

**Caddy** — append `deploy/Caddyfile.example` to `/etc/caddy/Caddyfile`, adjust
the hostname, then `sudo systemctl reload caddy`. TLS is automatic.

Both route by hostname, so Laam's existing configuration is untouched.

## 6. Verify

```bash
curl -s http://127.0.0.1:18080/api/health          # {"status":"ok",...}
curl -s https://targetexpress.example.com/api/health
```

Then sign in with a seeded account (`9000000001` / `target123`) and **change
every seeded password immediately** — they are published in this repository.

## Routine operations

```bash
# Logs
docker compose -f docker-compose.prod.yml --env-file .env.prod logs -f api

# Deploy an update
git pull
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
docker compose -f docker-compose.prod.yml --env-file .env.prod exec api alembic upgrade head

# Stop only this stack - Laam is unaffected
docker compose -f docker-compose.prod.yml --env-file .env.prod down
```

### Backups

The database is the business record: trips, odometer readings, invoices. Back it
up before the client has real data in it, not after.

```bash
docker exec tx-db pg_dump -U targetexpress targetexpress \
  | gzip > /var/backups/tx-$(date +%F).sql.gz
```

A nightly cron entry:

```
15 2 * * * docker exec tx-db pg_dump -U targetexpress targetexpress | gzip > /var/backups/tx-$(date +\%F).sql.gz && find /var/backups -name 'tx-*.sql.gz' -mtime +14 -delete
```

Proof-of-delivery photographs live in the MinIO volume `target-express_tx-minio-data`
and need their own backup once uploads are built.

## Before this carries real client data

These are not blockers for a demo, but they are blockers for production use:

- [ ] Change every seeded password
- [ ] Confirm the firewall exposes only 80 and 443 (`ufw status`) — the stack
      binds everything else to loopback, but verify
- [ ] Database backups running and a restore actually tested
- [ ] `SECRET_KEY` generated on the server, never reused from a laptop
- [ ] Decide log retention — GPS breadcrumbs and audit rows grow steadily
